# 2h → 30m 降档触发诊断与实验结果

日期：2026-11-04

## 结论

把 2h 战役接入现有 30m Mic 触发层，确实消除了“2h 是唯一未降档周期”的架构差异，
但没有修复交易语义。BTC 与四标的的 full/dev/test/1.5× 整体恶化，因此不能把该改动
作为生产修复；它会更早、更多地签发主张，却没有解决确认期间箱体几何与 claim 身份的
保持、迁移或失效。

## 先发现并修复的实验接线缺陷

`tools/replay_compounding.py --config` 最初只读取、哈希并快照实验配置，却没有把路径传给
`ScenarioRunner`。因此第一轮所谓实验实际仍使用生产配置，结果与基线逐项相同。

现已改为：

```python
ScenarioRunner(symbols, config_path=strategy_path, progress=progress)
```

并增加回归测试，防止“报告配置与实际执行配置分叉”。

真实实验配置仅改变：

```json
"trigger_tf_by_htf": {
  "2h": 1800,
  "4h": 7200,
  "12h": 7200,
  "1d": 14400
}
```

BTC 2h Mic 缓存实际生成 775 个事件，证明配置已接入。

## Mic 计数可观测性缺陷

此前 `go_events` 与 `mic_go_events` 使用原始配置白名单：

```text
ACCEPT / REJECT
```

实际事件对象使用规范 ID：

```text
BREAKOUT_ACCEPTED / LEVEL_REJECTED
```

路由器内部已经使用规范化白名单，因此交易一直真实发生；只有诊断计数长期显示为 0。
现已让计数使用与路由相同的 `_normalized_whitelist`。这是纯可观测性修复，不改变交易。

BTC 2h→30m 的计数修复前后：

| 场景 | go_events | mic_go_events |
|---|---:|---:|
| full 1× | 0 → 1,375 | 0 → 704 |
| dev 1× | 0 → 901 | 0 → 457 |
| test 1× | 0 → 474 | 0 → 247 |
| full 1.5× | 0 → 1,375 | 0 → 704 |

四份交易 CSV 的 SHA-256 在修复前后完全相同，权益与 closed 摘要也逐项相同。
四标的实验报告生成于计数修复前，所以其中两个计数仍为假零，但交易绩效有效。

## 对下一步的约束

1. 不把 `2h: 1800` 合入生产配置。
2. 不把“更早触发”解释为“更有效的原 claim”。
3. 下一步应贯穿 `claim_id / box_id / geometry_version` 生命周期，区分：
   - 同一 claim 在更细时钟上完成确认；
   - 确认期间箱体几何迁移，但 claim 合法迁移；
   - 原 claim 已失效，细周期事件只是旧结构的回声。
4. Mic 生命周期计数必须基于规范事件 ID，并继续拆分检测、白名单、路由拒绝、下单、成交。
