# BTC 单标的 Claim 生命周期报告

日期：2026-11-04  
范围：BTCUSDT，250 USDT，full/dev/test/full 1.5×；不讨论四标的资金分配。

## 1. 本轮只做可观测性

本轮没有增加入场门槛、价格过滤、周期关闭、强制止盈或保本参数，也没有改变任何交易
判定。新增的是只读生命周期事实：

1. `CREATED`：claim 所属结构区域出生；
2. `EVIDENCE_STARTED`：交易证据开始形成；
   - ACCEPT：首次外侧收盘/突破候选开始；
   - REJECT：本次试探极值形成；
3. `CONFIRMED`：事件被确认；
4. `ORDERED`：订单提交；
5. `FILLED`：真实成交；
6. `COMPLETED`：原 claim 到达目标；
7. `MIGRATED`：同根出现迁移接受，原仓由新主张重新承保；
8. `EXITED`：最终退出成交。

每笔交易同时导出：

- `claim_id / box_id / geometry_version`
- 出生、证据开始、确认、下单、成交、完成、迁移、退出时间
- 出生/确认/成交价格
- 创建时箱体上下沿、目标、失效位
- claim 出生环境与确认环境

产物：

- `full_1x.claim_events.csv`
- `full_1x.trades.csv`
- `lifecycle_trades.csv`
- `lifecycle_summary.json`

### 分周期：真正的证据与执行延迟

| 周期 | 笔数 | evidence→确认 中位/P90/最大 | 确认→成交 中位/P90/最大 |
|---|---:|---:|---:|

| 4h | 51 | 0h / 8h / 8h | 4h / 4h / 7h |
| 12h | 33 | 4h / 24h / 36h | 12h / 12h / 13h |
| 1d | 14 | 24h / 48h / 48h | 24h / 24h / 25h |

### 对 2h 问题的含义

此前“最多约 8 小时”把两个阶段混在了一起。现在可见：

- 典型 2h 单并没有长时间等待证据确认：中位为 0h；
- P90 的证据确认延迟是 4h，最大 6h；
- 确认后的典型成交延迟固定为 2h；
- 最大 9h 来自订单/成交路径尾部，而不是统一的确认根数。

所以不能简单缩短确认根数。下一步必须逐单区分：

1. 证据形成后确认是否仍引用同一 claim；
2. 确认后到成交期间 claim 几何是否保持、迁移或退役；
3. 延迟来自市价下一执行开盘，还是限价排队。

## 4. 退出生命周期

151 笔交易按原 claim 状态分组：

| 状态 | 笔数 |
|---|---:|
| 原 claim 未完成即退出 | 113 |
| 原 claim 完成后继续运行 | 36 |
| 原 claim 显式迁移 | 2 |

目前系统只有 2 笔显式迁移，而 36 笔到达原目标。说明“原 claim 完成后继续持仓但缺少
新主张”的问题确实存在，不是少数异常。

下一步退出治理应针对这 36 笔逐单分析：

- 完成后 MFE 继续扩张多少；
- 完成到退出经历多少小时/多少 bar；
- 最终实现相对完成时利润回吐多少；
- 哪些交易出现了新的外侧接受、顺向 pivot 或新箱体，可作为 runner claim 来源；
- 没有新主张的仓位不应被隐式视为无限期 runner。

不采用“到目标立即平仓”或固定 `+1R` 保本，因为已有反事实已经否定。

## 5. 环境问题

当前生产 `regime` 在 claim 出生到事件确认之间 151 笔全部未改变：

- TREND_DOWN → TREND_DOWN：41
- TREND_UP → TREND_UP：50
- RANGE → RANGE：10
- TRANSITION → TRANSITION：50

这不说明环境稳定，反而再次说明现有 `regime` 粒度太粗，无法表达此前已观察到的近期
3/5/8 日方向变化。

下一步环境实现应作为 claim 属性和轨迹，而非开仓门：

1. 出生时方向状态；
2. evidence 开始时方向状态；
3. 确认时方向状态；
4. 成交时方向状态；
5. 持仓期间方向状态迁移。

先并列导出 3/5/8 日及无固定窗口的结构方向，不依据结果挑选单一窗口，也不用于过滤。
